## 1. 这个画布到底是什么产品

在讨论功能之前必须先回答这个问题，否则功能清单会变成竞品功能的堆砌。

### 1.1 用户为什么会打开画布而不是工作台

| | Studio 工作台 | Canvas 无限画布 |
|---|---|---|
| **核心动作** | 批量出图 → 挑 → 下载 | 出一张 → 看 → 基于它再出一张 |
| **时间结构** | 一次性提交，等一批结果 | 连续的、有因果的迭代链 |
| **空间语义** | 时间流（最新在前） | **空间即记忆**（哪张从哪张来，一眼可见） |
| **典型用户** | 知道要什么，要 20 个候选 | **不知道要什么，在探索方向** |

**结论：画布的不可替代价值是「探索路径的可视化」**——`CanvasEdge` 记录的父子血缘就是这条路径。工作台永远无法表达「这张是从那张改来的」。

### 1.2 由此推出的三条设计红线

**① `edges` 必须保持只读血缘，不能变成用户可画的数据流**

ComfyUI/Krea 允许手动连线，前提是它们有 DAG 执行引擎去兑现这条线的语义。ImageHub 后端只是无状态转发——一旦允许用户画任意边，边的含义就从「血缘」漂移成「数据流」，而系统兑现不了这个承诺。

**② 不做类型化端口与颜色系统**

画布上只有一种数据（图片），端口颜色承载零信息量，只增加视觉噪声。

**③ 不做子图、条件、循环节点**

这三者的前提是多类型节点 + 编排引擎。右侧 360px 面板**本身就是** InvokeAI 意义上的 Linear View，再造表单构建器等于让用户搭一个他已经免费拥有的东西。

> 这三条不是保守，而是**避免把一个「探索工具」做成一个「弱化版 ComfyUI」**——那样两头不讨好。

## 2. 竞品给出的真正启示

调研了 27 个产品，分三类。**最有价值的发现不是某个炫酷功能，而是一条判断**：

> ImageHub 画布缺的**不是节点编排能力，而是画布的基线能力**。

tldraw 官方把 undo/redo、复制粘贴、拖放列为 **table-stakes**（入场门槛）。对照检查：

| 基线能力 | ImageHub 现状 |
|---|---|
| 撤销/重做 | ❌ 完全没有 |
| 框选多选 | ❌ `selectedNodeId` 是单值 |
| 复制粘贴 | ❌ 无 |
| 拖拽落图 | ❌ 无 |
| 视口裁剪 | ❌ 所有节点无条件渲染 |
| 批量生成 | ⚠️ 曾硬编码为 1，现已支持并发 |

**在补齐这些之前谈 inpainting、节点流，是本末倒置。** 用户会先因为「误删了一个节点无法撤销」而流失，而不是因为「没有局部重绘」。

三类产品的借鉴价值排序：

| 类别 | 代表 | 价值 |
|---|---|---|
| **开源画布 SDK** | tldraw、Excalidraw、React Flow | ⭐⭐⭐ tldraw 与本项目**同为 DOM + CSS transform 架构**，交互与性能方案可直接移植 |
| **AI 生图画布** | Krea、Firefly Boards、Weavy、Flora | ⭐⭐⭐ 生图交互的直接对标 |
| **节点流工具** | ComfyUI、InvokeAI、n8n | ⭐ 多数过重，只取局部（节点内进度、pin、便签） |

## 3. 功能规划：五个部分

### 第一部分 · 画布基线（P0）——「不做就不像画布」

| 功能 | 用户价值 | 参考 | 成本 |
|---|---|---|---|
| **撤销/重做** | 误删/误拖可挽回。**这是流失率最高的缺失项** | tldraw mark-based 批处理：一次拖拽合并成一条记录，`Esc` 走 bail 分支 | 高 |
| **框选多选** | 批量删除/导出的前置能力 | tldraw（`Shift` 加选、`Alt` 涂抹式框选更适合散乱布局） | 中 |
| **复制粘贴** | `Ctrl+V` 直接把剪贴板图片粘成节点 | Excalidraw | 中 |
| **拖拽落图** | 拖本地图片进画布 → 成为参考图节点 | Firefly Boards、Krea | 低 |
| **右键菜单** | 就地操作，不用跑到 360px 面板 | Excalidraw 三套菜单（空白/单选/多选） | 低 ✅ |

### 第二部分 · 性能（P1）——「节点变多后的生死线」

| 功能 | 用户价值 | 关键细节 | 成本 |
|---|---|---|---|
| **视口裁剪** | 100 个节点不卡 | 视口外 `display:none` **但保留 DOM**——卸载会导致图片重解码、滚回来闪白。选中节点与 generating 节点永不裁剪 | 中 |
| **LOD 分级** | 缩小时省内存，放大时清晰 | 按 `节点宽 × zoom × dpr` 选图源 | 中 ✅ |
| **交互层解耦** | 拖拽不掉帧 | 边线 SVG 层与网格层设 `pointer-events: none` | 低 |
| **缩略图移出主线程** | 压缩时不卡拖拽 | WebP 编码放进 Worker | 中 |

### 第三部分 · 生图交互（P2）——「画布相对工作台的差异化」

**这部分是画布的核心价值所在**，优先级应高于图像编辑。

| 功能 | 用户价值 | 参考 | 成本 |
|---|---|---|---|
| **右键「在此生成」** | 想在哪出图就在哪出，空间由用户掌控 | Recraft、Playground | 低 ✅ |
| **派生把手** | 从节点拖出一条线松手即建子节点——把「优化」从两步降为一个手势 | ComfyUI、Krea Nodes、n8n | 中 |
| **多图参考** | 选多张图作为同一次生成的参考，做风格融合 | Firefly Boards Remix | 中 |
| **扇形变体** | 一次产出 2–4 个分支并自动排布，**这是迭代树真正的用法** | Krea 扇出、Flora | 中 |
| **同参换种子** | 不改词只出同构变体，配 creativity 滑杆 | Krea Seed | 低 |
| **节点内分阶段进度** | 把黑盒等待变成可见进度。后端 `stages` **已存在**，零后端成本 | ComfyUI、Krita | 低 |
| **并发生成** | 一次铺多张，不用干等 | Studio `pumpQueue` 同构 | 中 ✅ |

### 第四部分 · 图像编辑（P3）——「从陈列变工作台」

⚠️ **全部依赖上游 API 能力**。当前 `/api/images/generate` 只做无状态转发，inpaint/outpaint 需要上游支持 mask 参数。**落地前必须先确认上游协议，否则是空中楼阁。**

| 功能 | 参考 | 成本 |
|---|---|---|
| 扩图 Outpaint（拖四边手柄扩出待生成区） | Playground、Midjourney、Krea | 高 |
| 局部重绘 Inpaint（框选/笔刷 + 该区域独立提示词） | Krea Change Region + Annotate | 高 |
| 手绘蒙版（`perfect-freehand` 输出闭合轮廓，可直接光栅化成 mask） | tldraw/Excalidraw 画笔基础库 | 高 |
| 流式局部预览（partial images） | OpenAI `partial_images`、Krea Realtime | 高 |

### 第五部分 · 组织与协作（P4）

| 功能 | 用户价值 | 参考 | 成本 |
|---|---|---|---|
| **便签/区域底板** | 在空间里写「这批给客户 A」。**不需要 group 数据结构**，垫在节点后面即得分组 | n8n Sticky Notes | 中 |
| **双图对比** | 选两张 A/B 滑块对比 + 参数 diff。图像评审刚需 | rgthree Image Comparer | 中 |
| **配方快照** | 把 prompt + params 存成可复用 chip | ComfyUI 模板 | 中 |
| **节点 Pin** | 防止评审时误拖已定稿的图 | n8n、ComfyUI | 低 |
| Frame 容器 | 批量生成的 N 张自动成组 | Excalidraw Frames | 高 |

## 4. 建议的实施顺序（含理由）

作为产品判断，我建议**不按 P0→P4 顺序做**，而是这样：

```
C0 架构拆分  →  C1 性能  →  C2 基线  →  C3 生图交互  →  C4 编辑/协作
   (已部分完成)     (P1)        (P0)         (P2)          (P3/P4)
```

**为什么性能（P1）排在基线（P0）之前？**

- 性能改动**局限在渲染层**，不碰数据模型，风险最低
- 而撤销/重做（P0 里成本最高的）要引入 history 栈，会**改变所有状态变更的写法**——应该等数据模型稳定后再做
- 用户当前的实际痛点是「图糊」「卡」，不是「不能撤销」（因为节点还不多）

**为什么生图交互（P2）优先于图像编辑（P3）？**

- P2 是画布的**差异化价值**（探索路径），P3 是**通用能力**（很多工具都有）
- P3 全部卡在上游 API，不确定性最高

**如果只能做三件事，我建议：**

1. **视口裁剪 + LOD**（P1）——直接解决卡与糊
2. **派生把手 + 扇形变体**（P2）——把「迭代树」这个核心卖点真正做出来
3. **撤销/重做**（P0）——用户信心的底线

## 5. 架构拆分（C0）

### 5.1 为什么必须先拆

Canvas 代码在 `src/App.tsx` 里是连续的 **1479 行**（`CanvasNodeView` 50 行 + `CanvasPage` 1419 行），加上 CSS 754 行。上面任何一个 P0/P1 功能都会让它继续膨胀。

**一个有利前提**：`CanvasPage` 是顶层函数，**不捕获 App 的任何闭包变量**，只通过 7 个 props 通信——天然可抽离。

### 5.2 关键约束：不能只抽 Canvas

CanvasPage 依赖 **20 个与 Studio 共用的函数**。只抽 CanvasPage 会形成 `App.tsx → CanvasPage.tsx → App.tsx` **循环 import**，模块初始化顺序脆弱（尤其 `runtime*` 的 `let` 和 `PROTOCOLS` 顶层常量）。

**必须先抽共享层**，做成不 import `App.tsx` 的叶子模块：

```
src/
├── shared/          # 叶子模块，绝不 import App.tsx 或 canvas/
│   ├── types.ts         ImageProtocol / ImageParams / ApiConfig…    ~40 行
│   ├── modelSizing.ts   模型族判定 + 尺寸表 + PROTOCOLS             ~410 行
│   ├── imageUtils.ts    blobToDataUrl / createListThumbnail…       ~200 行
│   ├── db.ts            openDb（唯一实现）+ history 系列            ~150 行
│   ├── utils.ts         uid / clampNumber / readApiJson            ~90 行
│   └── appConfig.ts     runtime* 单例 + normalizeApiBaseUrl        ~130 行
├── canvas/
│   ├── types.ts         CanvasNode / CanvasEdge…                   ~50 行
│   ├── canvasDb.ts      6 个画布 IndexedDB 函数                     ~54 行
│   ├── CanvasNodeView.tsx                                          ~55 行
│   └── CanvasPage.tsx                                              ~1419 行
└── App.tsx          13000 → 约 10400 行
```

配置仍由 `shared/appConfig` 统一读取，满足「配置统一读取」的要求。

### 5.3 五个必须避开的坑

| # | 坑 | 后果 |
|---|---|---|
| 1 | **`.canvas` 不是 Canvas Mode** —— styles.css:2518 的 `.canvas` 是 **Studio 主滚动区** | 按 `grep canvas` 搬 CSS 会**直接搞坏 Studio 布局**。Canvas Mode 准确范围是 7836–8589，全带 `canvas-` 前缀 |
| 2 | **`openDb` 是隐蔽耦合点** —— CanvasPage 正文 0 次引用，但 6 个画布 IDB 函数全调它，且它的 `onupgradeneeded` 同时建 **三个 store** | 复制一份 = 两套 upgrade 逻辑漂移 → 用户端 store 缺失或 VersionError |
| 3 | **`runtime*` 是可变单例** | 各持一份 → 「后台改了上游站点，画布仍打旧地址」这类极难排查的 bug |
| 4 | **`tsconfig` 没开 `noUnusedLocals`** | 搬完后 App.tsx 的死代码不报错，会静默留下两份 `canvasThumbKey` |
| 5 | **CSS 令牌顺序** —— `.canvas-page` 靠自身作用域重定义 `--bg` 实现局部深色 | 拆成独立 CSS 后若注入顺序排到 `:root` 前，会退回「亮框架 + 黑画布」撕裂 |

### 5.4 实施纪律

**分两步，不要合并**：先**纯搬迁**（逐字搬运，`git diff` 可校验等价性），再**重构**（CanvasPage 里 3 处结构雷同的 `/api/images/generate` 调用值得合并，但那是独立一次改动）。

**验证**：`tsc -b` 只保证类型接得上，接不住「CSS 顺序错了」「IndexedDB 建表没执行」「runtime 配置没同步」三类运行时回归。必须人工走：冷启动加载历史画布 → 生成 → 优化 → 刷新确认持久化。

## 6. 与后台异步生成的关系

见 [async-generation-prd.md](async-generation-prd.md)。要点：

- 当前**不是**异步架构，前端一关连接就断
- 但服务端 handler 会跑完、图会落盘、`request_logs` 会更新——**图早生成好了，只是前端不知道**
- 所以是「补回读链路」而非「重写队列」，`request_logs` 已具备任务表全部字段

**对画布的影响**：画布节点重载时那个「生成中断（页面关闭）」是**误判**，P0 对账完成后应改为「正在恢复…」再拉真实状态。
