优先级

价值与成本的分布

横轴是实现成本，纵轴是用户价值。右上角不是「最该做」，而是「要排期做」；左上角才是应该立刻做的。

建议

如果只做三件事

01视口裁剪
+ LOD

为什么第一：这是你现在真实感受到的痛点——图糊、节点一多就卡。而且改动局限在渲染层，不碰数据模型，风险最低。

+100 个节点不卡；缩略图基础设施已就绪，只差按 zoom 切换
+可随时回滚，不影响任何已有数据
−裁剪必须用 display:none 保留 DOM，卸载会导致图片重解码、滚回来闪白
02派生把手
+ 扇形变体

为什么第二：这是把「迭代树」这个核心卖点真正做出来的一步。现在的边只是优化操作的副产品，用户感知不到它是一棵可探索的树。

+从节点拖出一条线松手即建子节点——把「优化」从两步降为一个手势
+一次产出 2–4 个分支并自动扇形排布，分支比较才是画布相对工作台的差异化
−要克制：只做「父图→优化子图」这一种连接，不能滑向 ComfyUI 式的自由连线
03撤销
/ 重做

为什么第三而不是第一：它成本最高，且会改变所有状态变更的写法（要引入 history 栈）。应该等数据模型稳定后再做，否则每加一个功能都要补一次历史记录。

+用户信心的底线，误操作可挽回
−必须用 mark-based 批处理：一次拖拽合并成一条记录，否则拖一下产生几十条 undo
竞品

别人是怎么做的

调研 27 个产品，分三类。对你最有参考价值的是第一类——tldraw 与本项目同为 DOM + CSS transform 架构，方案可直接移植。

产品类型值得抄的一件事要不要抄
tldraw开源画布 裁剪用 display:none 保留 DOM 而非卸载；选中节点永不裁剪 抄
Excalidraw开源画布 三套右键菜单（空白 / 单选 / 多选），菜单项右对齐显示快捷键 已抄
React Flow节点图 NodeToolbar 不随视口缩放——缩到 20% 时按钮仍可点 抄
Krea NodesAI 画布 拖出把手 → 自动列出可连接候选，比先建节点再连线少一步 抄手势
Firefly BoardsAI 画布 框选多图 → 浮出 Remix → 出一组融合变体 抄
n8n工作流 便签垫在节点后面即得分组，不需要 group 数据结构 排期
ComfyUI节点流 类型化端口 + 自由连线 + 子图嵌套 不抄
最重要的一条判断：不要做成 ComfyUI。 它的端口配色是为了在十几种数据类型间做校验，而你的画布只有图片一种数据，颜色承载零信息量。 更关键的是——一旦允许用户手动画任意边，边的含义就从「血缘」漂移成「数据流」，而后端并没有 DAG 执行引擎去兑现这个承诺。
商业化

四条路径，按「地基完成度」排序

判断依据不是市场想象，而是代码里已经存在什么。有些路径的基础设施你已经建好了，只是还没接上收费。

路径 A · 算力分销

地基已完成 ~80%

用户不带 Key，平台代充上游额度，赚差价。

关键事实：OAuth 登录成功后，服务端已经在自动下发 apiKey 给前端。也就是说「平台发 Key」这套架构你已经建好了。 再加上已有的每日生成配额、每用户磁盘配额、按用户分目录存图——计费所需的计量基础设施全都在。

+差价模式现金流直接，用户零配置上手（不用自己找 Key）
+只差三件事：额度账本、充值入口、超额拦截（配额拦截已有）
−要垫付上游成本，需要防刷（当前 clientId 可伪造，得先接 OAuth 强鉴权）
−与 local-first 定位有张力：用户会问「我的图是不是在你服务器上」

路径 B · 企业私有部署

地基已完成 ~60%

一次性授权 + 年维护费，部署在客户内网。

关键事实：deploy.sh 已支持一键部署（含 systemd、Nginx 反代示例），数据全部落本地 .data/。 local-first 在这里从「技术选择」变成「销售卖点」——设计素材不出内网，是广告、游戏、影视公司的硬需求。

+客单价高，不垫付算力成本，客户自带上游账号
+管理后台、配置中心、审计日志、配额——企业要的治理能力已经有了
−缺多用户体系（当前只有单管理员 + clientId），要做角色与团队空间
−销售周期长，需要交付与支持能力

路径 C · 模板与配方市场

地基已完成 ~35%

行业工作流、画册模板、参数配方，创作者上架分成。

关键事实：已有 8 个行业 Agent、画册多页编排流程、配置中心的预设管理。 广场提供了内容与流量入口。缺的是「配方」这个可交易的最小单元——把 prompt + 参数存成命名快照。

+边际成本近零，且强化社区粘性
+与画布的「配方快照」功能天然同源，做一次两用
−需要足够的创作者密度才能转起来，早期是冷启动难题
−提示词易被复制，需要设计「用得到但拿不走」的分发方式

路径 D · 协作 SaaS

地基已完成 ~15%

团队共享画布、实时协作、版本与评论。

关键事实：这是 Freepik Spaces、Figma Weave 的路线，也是最拥挤的赛道。 而你当前的画布状态存在浏览器 IndexedDB，协作需要把状态搬到服务端——这与 local-first 定位正面冲突，是一次架构方向的改变而非增量。

+订阅制天花板最高
−要重写状态层（IndexedDB → 服务端 + 冲突合并），是重构不是加功能
−正面对上 Figma/Adobe，差异化难立
建议：短期走 A（算力分销）——地基最全，只差账本和充值；中期做 B（私有部署），把 local-first 从技术特性变成销售话术。 C 作为 B 的附加值捆绑。D 暂时不碰，它要求你放弃 local-first，而那恰恰是你现在唯一的结构性差异点。
前置

动功能之前，先拆代码

画布代码在 src/App.tsx 里是连续的 1479 行，加 CSS 754 行。上面任何一个功能都会让它继续膨胀。 好消息是 CanvasPage 是顶层函数、不捕获 App 的任何闭包变量，天然可抽离。

但不能只抽画布：它依赖 20 个与工作台共用的函数，只抽会形成循环 import。必须先抽共享层做成叶子模块。

!.canvas 不是画布——它是工作台主滚动区。按 grep 搬 CSS 会直接搞坏工作台布局
!openDb 建三个 store，复制一份会导致两套 upgrade 逻辑漂移 → 用户端 VersionError
!runtime* 是可变单例，各持一份会出现「后台改了站点，画布还打旧地址」
完整规格见 docs/canvas-v2-prd.md · 异步生成方案见 docs/async-generation-prd.md · 缩略图方案见 docs/thumbnail-prd.md
