# 生成任务后台化（Async Generation PRD）

> 状态：方案待评审，未实施。
> 目标：关闭页面后生成继续，重新打开能拿回结果。

---

## 〇、先纠正一个前提

> 「我们现在图片生成是扔到后台，也就是服务器后台去异步执行的」

**这个前提目前不成立。** 当前是**同步转发**架构：

```
前端 fetch /api/images/generate
  └─ 服务端 await 上游 API（几十秒）
      └─ 落盘 → 写 request_logs → sendJson 返回
          └─ 前端拿到响应才知道结果
```

前端关闭页面 = HTTP 连接断开 = **前端永远拿不到这次结果**。你截图里那个「生成中断（页面关闭）」就是这么来的。

## 〇之二、但有个有利事实（决定了改造成本）

我查了代码，**服务端其实已经把活干完了**：

- Node 的 async handler **不会**因为客户端断开而中止，`await fetch(上游)` 会正常跑完
- 图片会正常落盘到 `.data/images/`
- `request_logs` 里的 status 会正常从 `running` 更新为 `success`
- 只有最后 `sendJson` 写进了一个已关闭的 socket，静默失败

**也就是说：图早就生成好了，只是前端不知道、也没途径查。**

更关键的是，`request_logs` 表已经具备任务表的**全部**字段：

| 列 | 用途 |
|---|---|
| `request_id` (PK) | 任务 ID（每次生成已有 randomUUID） |
| `client_id` | 归属，可按客户端查自己的任务 |
| `status` | `running` / `success` / `error` |
| `created_at` | 排序与增量拉取 |
| `image_saved` / `data.savedImages` | 产物位置 |

**所以这不是「重写成异步队列」，而是「补一条回读链路」。** 成本比看上去低一个数量级。

---

## 一、方案分级

### P0 · 结果找回（推荐先做，成本最低、收益最大）

不改生成链路，只补查询与恢复。

**1. 新增公开接口 `GET /api/tasks`**

```
GET /api/tasks?clientId=<id>&since=<timestamp>
→ { ok, tasks: [{ requestId, status, model, prompt, createdAt, durationMs,
                  images: [{ url, thumbUrl, width, height }], error }] }
```

- 鉴权沿用项目现有的 `clientId` 语义（与生成配额、`/api/images/thumb` 一致）
- 只返回该 `clientId` 自己的记录，直接从 `request_logs` 读，**无需新表**

**2. 前端提交即落盘 pending 记录**

现在是「拿到响应才写 IndexedDB」，改成「发出请求就写一条 `status: "running"` 的记录」，带上 `requestId`。这样刷新/关页面后本地仍知道「有一个任务在跑」。

**3. 重连时对账**

页面加载后：
- 找出本地所有 `status === "running"` 的记录
- 调 `/api/tasks` 拉服务端真实状态
- 服务端已完成 → 拉图、补齐本地记录、更新画布节点
- 服务端仍在跑 → 保持 running，继续轮询
- 服务端查无此记录 → 才标记为失败

**这一步直接消灭「生成中断（页面关闭）」**——那个状态本来就是误判。

**改动量**：后端 1 个接口（约 40 行），前端 1 个对账 effect + 提交时机调整。**不动生成链路，风险低。**

### P1 · 真正的服务端队列

P0 解决「结果找回」，但有两个 P0 覆盖不了的场景：

1. 关页面后**新发起**的任务（不存在，因为发起动作在前端）
2. **服务端并发控制**（现在前端关了，服务端还在跑，无人限流）

如果要这两个，才需要真队列：

```
POST /api/images/generate  → 立即返回 { taskId, status: "queued" }
服务端队列 worker 消费（并发上限可配）
GET  /api/tasks/:id 或 SSE /api/tasks/stream 获取进度
```

**代价**：生成链路要重写，前端从「同步等待」改成「提交 + 订阅」，`stages` 时间戳、错误处理、重试逻辑全部要跟着改。而且服务端进程重启会丢队列（除非任务表持久化 + 启动时恢复）。

**建议**：先做 P0。P0 上线后观察，如果没有「关页面后还要发起任务」的真实需求，P1 可以不做。

### P2 · 实时推送

用 SSE 替代轮询（项目已有 SSE 先例：`/api/prompt/analyze`、`/api/agent/analyze`）。属于体验优化，不影响正确性。

## 二、与画布并发的关系

你提的「画布最多 6 个并发」和这件事是耦合的：

- **P0 方案下**：并发控制在前端做（和 Studio 的 `pumpQueue` 一致，`concurrency` 上限 6）
- **P1 方案下**：并发应该移到服务端队列，前端只管提交

**所以建议等架构方向定了再实现并发**，否则前端刚写完的闸门，做 P1 时要拆掉。

## 三、风险与边界

| 风险 | 说明 |
|---|---|
| **孤儿任务** | 服务端跑完但前端永远没回来查 → 图片占着磁盘。已有 5000 条日志裁剪会连带清理，但可能滞后 |
| **clientId 可伪造** | `/api/tasks` 用 clientId 查询，别人猜到 clientId 就能看到你的任务列表（含提示词）。当前 `/api/feedback`、`/api/images/thumb` 也是同样的信任模型。**若要更强隔离，需要接 OAuth 会话** |
| **进程重启** | P0 不受影响（状态在 SQLite）。P1 的内存队列会丢，需要启动时从任务表恢复 `queued` 记录 |
| **配额绕过** | 现在配额在生成入口检查。若改成队列，要确保入队时也检查，否则可以刷一堆任务入队 |

---

## 四、建议

**先做 P0。** 它用约 40 行后端 + 一个前端对账 effect，就能解决你截图里的实际问题（关页面后白跑），且不碰生成链路、可随时回滚。

P1 是真正的架构改造，建议等 P0 跑一段时间、确认还需要什么之后再决定——避免为了一个「听起来应该有」的能力重写整条生成链路。
