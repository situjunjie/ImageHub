# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Product

ImageHub / Image Studio (`codex-image-batch-studio` in package.json) — a local-first batch image-generation workbench. The user fills in an upstream API URL + key, picks an `image-2`-class model, and submits batches; the browser keeps a full copy in IndexedDB, and generated images are also persisted server-side under `.data/images/` (served via the two-segment `/api/images/local/<userDir>/<file>`) so the admin dashboard can review them alongside request logs. Four major feature surfaces: **Studio** (batch generation), **Canvas** (infinite canvas generation mode), **Square** (community gallery with recommend/like), and **Agent Mode A** (NLP-driven brochure planning). Admin dashboard tracks request metadata plus saved-image file references — API keys are never persisted server-side. README.md (Chinese) is the canonical product spec; `docs/agent-mode-brochure-prd.md` is the Agent Mode A spec; `docs/canvas-mode-prd.md` is the Canvas Mode spec.

## Commands

```bash
npm install          # one-time (better-sqlite3 is native, compiles here)
npm run dev          # Vite dev server on http://localhost:8877 (port hardcoded)
npm run build        # tsc -b && vite build  — TypeScript check is gated here
npm run build:server # esbuild-bundle the standalone production server → server-dist/index.mjs
npm run start        # run the production server (serves dist/ + all /api/*), PORT env overrides 8877
./deploy.sh          # full server deployment: deps → build → restart (also start|stop|restart|status|systemd)
```

**Production deployment (since 2026-07):** the backend no longer requires the Vite dev server. `registerApiRoutes(app)` (exported from vite.config.ts) is the single source of truth for all API routes; the dev plugin mounts it on Vite's connect middlewares, and [server/index.ts](server/index.ts) mounts the same function on a plain Node http server with connect-compatible prefix stripping, plus dist/ static hosting (SPA fallback, immutable cache for /assets, no-cache for index.html + build-version.json) and `/healthz`. Taiji OAuth is preserved: env vars come from `.env` (template auto-generated by deploy.sh); redirect URI auto-derives from Host/X-Forwarded-Proto when `OAUTH_REDIRECT_URI` is unset, so it works behind nginx.

There is **no test framework, ESLint, Prettier, Biome, or pre-commit hook** in this repo — don't go hunting for them. There is no standalone `typecheck` script either; `tsc -b` runs as part of `npm run build`. Use that to check types.

Admin defaults: `admin` / `admin123456` at `http://localhost:8877/#admin` (dev fallback in `vite.config.ts`; first login forces a reset). Override via env: `ADMIN_USERNAME=... ADMIN_INITIAL_PASSWORD=... npm run dev`. Don't echo this password in UI copy or generated `.env` templates — deployments would ship it verbatim.

## Architecture — the non-obvious parts

**The entire backend lives inside `vite.config.ts`** (~6000 lines) — every `/api/*` route is implemented in the exported `registerApiRoutes(app)` function there. `server/index.ts` (~140 lines) is only a thin production host: it mounts that same function on a plain Node http server and adds static hosting. There is no `api/` or `backend/` directory, and no per-route files. When the task involves request logging, admin auth, the upstream proxy, or reference-image temp URLs, edit `vite.config.ts`, not `server/index.ts` and not files under `src/`.

Server-side route groups:
- `/api/models`, `/api/images/generate` (enqueue, 202), `/api/tasks` (client polls task results), `/api/images/thumb` (client posts back a browser-made thumbnail), `/api/prompt/analyze` (SSE), `/api/reference-images/:id` — core generation. Note the reference route is `/api/reference-images/:id`; there is no `/api/temp-reference`.
- `/api/auth/oauth/*` — Taiji OAuth login flow.
- `/api/admin/*` (login, logout, change-password, stats, requests, me) — admin dashboard.
- `/api/square/*` (feed, quota, recommend, like, image/:id, admin/overview, admin/export) — community gallery. Data persisted to `.data/square-store.json`. Feed/quota GET endpoints authenticate via `x-imagehub-api-key` header (not query params). Thumbnails are served as binary from `/api/square/image/:id` with long cache headers — the feed response returns `thumbnailUrl` (not inline base64) and deliberately omits `imageId`.
- `/api/agent/analyze` — Agent Mode A intent classification (single_image, multi_image_batch, brochure_project, page_refine).

**Frontend layout (post-C0 split, 2026-07-27):** `src/App.tsx` (~11500 lines) holds home, studio, square, and admin views via an `activePage` state switch (`"home" | "studio" | "square" | "admin" | "canvas"`) — no router library, no Redux/Zustand, no Context. The canvas-v2-prd §5 split is DONE: `src/shared/` (types, modelSizing, imageUtils, db, utils, appConfig, AppNav — leaf modules that never import App.tsx or canvas/) and `src/canvas/` (types, canvasDb, CanvasNodeView, CanvasPage ~3000 lines). `openDb` in `shared/db.ts` is the **only** IndexedDB upgrade entry (DB version 4: history + canvas-state + canvas-images + recipes + reference-library); the `runtime*` config singletons live only in `shared/appConfig.ts`. State is `useState` + `useRef`.

**Routing is hand-rolled hash routing** — there is no router library, but there *is* real routing, and it has three parts that must stay in sync: `pageFromHash()` maps `#studio`/`#square`/`#canvas`/`#admin*` → `activePage` (default home); a `hashchange` listener re-derives `activePage` so browser back/forward works; and page switches call `window.history.pushState(null, "", "#…")`. An IIFE `normalizePathToHash()` runs **before React mounts** and `replaceState`s bare paths (`/studio`, `/canvas`, `/square`, `/admin`, `/login`) into `/#<path>` — without it the production SPA fallback serves index.html with an empty hash and every path direct-link silently lands on the home page. Admin sub-tabs are deep-linked the same way (`#admin/logs|config|feedback|security`), read once for the initial `adminTab` state and written back by `selectAdminTab`.

Styles are all still in `src/styles.css` (plain CSS + tokens; canvas CSS was deliberately NOT split — `.canvas` in styles.css is the Studio scroll area, not Canvas Mode).

**Unified navigation (2026-07-27, user mandate):** all four main pages render `AppNav` (src/shared/AppNav.tsx) inside a header carrying the `.app-topbar` shell class (defined at the END of styles.css to win the cascade): identical 56px height, padding, hairline, surface background on every page. Fixed order 首页/工作台/画布/广场, active page shown with indicator (never "omit self"), no compact variant. The 工作台 item carries a running-task count badge; task completion on other pages fires an `appNotice` toast. Cross-page flows: Studio record「在画布中打开」(canvasImport payload → CanvasPage effect), canvas node「发送到工作台」, square「用同款参数生成」.

**Canvas Mode (infinite canvas):** `CanvasPage` component — a 2D pan/zoom canvas where users generate images as nodes and build visual iteration trees. URL hash `#canvas`. Layout: left = infinite canvas (DOM + CSS `transform` approach), right = 360px collapsible panel. Nodes stored as `CanvasNode[]` with position/status/image data; `type: "image" | "note"` — note nodes are plain text stickies with no image and no generation involvement. Edges (`CanvasEdge[]`) visualize parent→child optimization lineage via SVG bezier curves. `CanvasGroup[]` (id/name/nodeIds/collapsed) is a *flat* overlay — members keep absolute coordinates, a group is just a titled frame plus a batch-move handle, never a parent coordinate space. Canvas state persisted to IndexedDB stores `canvas-state` (single "current" key) and `canvas-images` (keyed by nodeId). Key state: `canvasNodes`, `canvasEdges`, `canvasGroups`, `viewport` ({x,y,zoom}), `selectedNodeId`/`selectedIds`, `panelMode` ("generate" | "optimize"). Generation reuses existing `/api/images/generate` — no new backend endpoints; recommend-to-square reuses `/api/square/recommend` with `sourceType: "canvas"`. Reference image compression for optimization uses `createSquareThumbnail()` (max edge 1024px, WebP 0.82). Snapshot export rasterizes groups + edges + notes + original-resolution images onto an offscreen `<canvas>` (max edge 6000px).

Canvas baseline interactions: snapshot-based **undo/redo** (⌘Z/⇧⌘Z), marquee multi-select (Shift additive, intersect not containment), clipboard paste + drag-drop of image files into reference nodes, per-node context menus, minimap (`M`), and canvas-side task reconciliation (requestIds persisted into nodes; the "任务对账" effect in CanvasPage recovers still-running generations via `GET /api/tasks`, with a 24-miss ≈ 2min "任务已丢失" deadman so nodes can't spin forever). Iteration-chain UX (2026-07-27): optimize inherits source params, auto-selects the new child, auto-pans the viewport, and on completion auto-switches the optimize source to the finished child; viewport position persists (1s debounce). Right-click "在此生成" opens an **inline composer card** at that spot (prompt + model/aspect/resolution, Enter submits via `handleCanvasGenerate({at, promptOverride})`). D-features: derive handle on selected node's right edge (drag out → optimize child at drop point), fan-out variants (optimize 数量 1–4), seed reroll (context menu, child variant below), A/B compare (exactly 2 selected), node pin (`pinned` skips drags), extra optimize refs (max 2, context menu「加为优化参考」). `docs/canvas-v2-prd.md` §7 progress table lags the code; trust the code.

Three Canvas invariants that are easy to break silently:
- **Undo/redo is snapshot-based** (`markHistory()` captures nodes+edges+groups *before* a mutation; one gesture = one snapshot — drags/note edits mark once at gesture start, not per frame). Every new mutation path must call `markHistory()` first or that operation silently becomes un-undoable. Corollary: deleted/undone nodes' blobs deliberately **stay** in `canvas-images` (and their objectUrls are not revoked) so undo can restore them — only `cleanupOrphanImages` on unmount reclaims them. Don't "fix" that as a leak.
- **Culling** (`applyCulling`) sets `display:none` on off-screen nodes by writing DOM style directly, and only reruns on viewport/nodes/selection change plus a `ResizeObserver`. It bails when the container measures 0×0 — without that guard the first paint hides every node until the user pans.
- **Orphan-image cleanup** on unmount is gated on `canvasLoadedRef.current`. StrictMode's throwaway mount/unmount fires cleanup before the async load lands, and an ungated cleanup reads an empty `nodesRef` and wipes every image out of `canvas-images`.


**Model variants:** `gpt-image-2` and `gpt-image-2-pro` use explicit 2K/4K size options (`GPT_IMAGE_2_SIZE_OPTIONS`) instead of pure aspect-ratio scaling, including duplicate-ratio 2K choices such as `2560x1440` and `2048x1152`. Other image-2 family models still fall back to fixed official 1K sizing via `usesOfficialGptImageSizing()`. Keep the frontend and backend size tables in sync.

**Square (community gallery):** users can recommend generated images to a shared feed. Browse by latest/hot/top; daily quotas (10 recommends, 10 likes). Admin has overview + CSV/JSON export. Square state is server-persisted in `.data/square-store.json`, not IndexedDB.

**Agent Mode A (brochure workflow):** toggleable mode that NLP-parses the prompt into an intent (single image → direct generation, multi-image batch → parallel generation, brochure project → multi-page planning with style-board selection). Brochure flow: analyze → plan → generate 4 style boards → user picks one → refine individual pages. Key state: `isAgentModeEnabled`, `agentModeState`, `agentModePendingPlan`, `agentModeBrochureDraft`.

**Data storage (SQLite + JSON + files):** As of 2026-07 request/generation records live in **SQLite** (`.data/imagehub.db`, via `better-sqlite3`), not JSON. The `request_logs` table has indexed columns (status, model, error_key, created_at, client_ip_hash, ref/upstream/image flags) plus a `data` TEXT column holding the full `RequestLog` JSON. `createRequestLog`/`updateRequestLog` are the only writers (`requestLogRow` upserts); reads are in `/api/admin/{stats,requests,requests/:id,logs/export}`. On first DB open, legacy `admin-store.json` `requestLogs` are migrated in once and cleared. Kept at 5000 rows (see the trim-order note in the privacy section — it is **not** plain oldest-first). **Adding a column requires an explicit `ALTER TABLE`:** `CREATE TABLE IF NOT EXISTS` silently does nothing to an existing table, so the DB-open path checks `PRAGMA table_info` and migrates + backfills (that's how `client_ip_hash` was added). **Still JSON:** admin users + audit logs (`admin-store.json`), config (`config-store.json`), square data (`square-store.json`) — these are config-like, not append-heavy records. `better-sqlite3` is a native dep (`npm install` compiles it); `@types/better-sqlite3` is a devDep.

**Image storage (per-user folders):** Generated images are saved to `.data/images/<userDir>/<requestId>[-<index>].<ext>` — `userDir` is an opaque HMAC-derived token (`imageDirToken`, see the privacy section), *not* the username or clientId; filename is the generation's `requestId`. Served via `/api/images/local/<userDir>/<file>` with `LOCAL_IMAGE_PATH_PATTERN` + `..` guard + `startsWith(LOCAL_IMAGE_DIR)` check against traversal. `savedImages[].id` stores the relative `<userDir>/<file>` path, so pre-existing images under the old plaintext directories keep resolving without any file migration. Each generate call already has a unique `requestId` (randomUUID) = the per-submission ID.

**Feature requests (2026-07-27):** SQLite table `feature_requests` (id, api_key_hash, content_raw, content_polished, status pending/planned/done/rejected, admin_reply, timestamps). Anti-abuse is three-layered and structural: submission requires an API key (only its sha256 via `hashApiKey` is stored — never the key), the server-side slider captcha (`issueCaptcha`/`verifyCaptcha`, same one-time-token system as admin login), the `feature` anon rate bucket (5/min/IP) plus 10/day per key hash. Content is LLM-polished via the user's own key/baseUrl (`/v1/chat/completions`, 30s cap, whitelist-validated baseUrl; any failure falls back to raw) and both raw+polished pass `redactCredentialText` before insert — users paste their own keys into feedback text. Routes: public `/api/feature-requests` (`/captcha`, `/mine` via `x-imagehub-api-key` header, POST), admin `GET/PUT /api/admin/feature-requests[/:id]` inside the admin dispatcher (post-auth). Admin UI: 用户反馈 tab (`#admin/feedback`); user UI: FeedbackModal from the Studio topbar (reuses `SliderCaptcha`). The admin list exposes only `api_key_hash.slice(0,6)` as a user tag.

**Analytics & feedback (2026-07):** Two more SQLite tables beyond `request_logs`: `daily_stats` (date+model PK, incremented once when a generation reaches terminal state via the `updateRequestLog` running→terminal transition guard; backfilled from existing logs when empty — daily trends survive the 5000-row trim) and `image_feedback` (one 👍/👎 per requestId, upserted via public `POST /api/feedback`). `GET /api/model-stats` (public) returns 7-day per-model successRate/P50/samples/ratings; the studio model picker renders this under each model (needs ≥3 samples). **Metric scoping:** `/api/admin/stats` headline numbers, modelCounts and errorCounts count image_generation requests ONLY (`analysisCount` reported separately); latency is P50/P95 over successful generations, not mean. Generation quotas live in config `quotas`: `generationDailyLimit` (per clientId per Shanghai calendar day, plus a per-IP ceiling at `GENERATION_IP_QUOTA_FACTOR ×` that) and `userDiskLimitMB` (per user image dir, walked with statSync across both the token dir and the legacy plaintext dir) — 0 = unlimited, enforced in the generate route with HTTP 429.

**Full error capture:** On generation failure the log stores `errorFull` — the complete upstream/relay error body (image data redacted, capped at 60k chars, not the 800/2500 truncation used for the summary fields). Rendered in the admin request detail as a red "完整错误内容" panel. This exists specifically to debug relays that return a 200/OK-looking response but actually failed generation.

**Generation pipeline (fully async since 2026-07, commit 88477c1):** the POST no longer waits for the upstream — generation runs in a **server-side queue**, so closing the page no longer loses results.
1. Client builds `Job` objects with a **pre-allocated `requestId`** (randomUUID, generated client-side before the request), pushes them onto `pendingQueueRef.current`, and `pumpQueue()` drains them respecting client-side `concurrency` (1–6).
2. Each job POSTs to `/api/images/generate` with `{ requestId, clientId, baseUrl, apiKey, request: { protocol, model, prompt, referenceImages, aspectRatio, seed, ... } }`. The server validates (model allowlist, quotas), accepts the client-supplied `requestId` only if it is UUID-shaped and unused, then **enqueues and returns 202 immediately** with `{ requestId, status: "queued", queue: {queued,running,capacity}, stages }`.
3. Server-side queue: `generationQueue` array drained by `pumpGenerationQueue()` — `GENERATION_MAX_CONCURRENCY = 4`, depth cap 200 (503 `队列已满` when full), queued tasks dropped after a 30-min TTL. Execution continues regardless of whether the client is still connected.
4. During execution, reference images (sent as data URLs) are stashed in the in-memory `temporaryReferences` Map with a ~10-minute TTL; the server forwards `/api/reference-images/{id}` URLs (not base64) to the upstream `/v1/images/generations` endpoint.
5. On success the server persists each generated image to `.data/images/<userDir>/<requestId>[-<index>].<ext>` (`persistGeneratedImages`; `userDir` = the opaque `imageDirToken`) and writes the result — status, `savedImages` (id=relative path, mime, bytes), local URLs (`/api/images/local/<userDir>/<file>`, immutable cache) — into the `request_logs` SQLite record. That record is the **only** place the result lands; there is no HTTP response carrying it. Records are capped at 5000; trimmed ones get their image files deleted too (`deleteSavedImages`) — see the trim-order note in the privacy section. Never the API key.
6. Client reconciliation: an effect in App.tsx (search "任务对账") polls `GET /api/tasks?clientId=...&ids=...` while any job is `queued`/`running` — the endpoint returns the caller's recent (24h/200-row) generation tasks from `request_logs`, plus any explicitly named ids **if they belong to that clientId**. This same path recovers results after a page reload; Canvas persists pre-allocated requestIds into its nodes for the same reason. The `/api/tasks` response must stay field-complete (stages, batchId/batchIndex/batchTotal, agent*, params) — it is the frontend's sole data source for restored records.
7. Both success and error paths record a `stages` object (`receivedAt`, `upstreamRequestedAt`, `upstreamRespondedAt`, and on success `imageSavedAt`/`returnedAt`) used for per-phase timing in the studio UI and admin log detail. Add new timestamps to both branches or the error path silently loses them.
8. Client fetches the image blob from the local URL (`generatedImageToBlob`, with `dataUrl` fallback) and stores Blob + history record in IndexedDB, then uploads a browser-made thumbnail via public `POST /api/images/thumb` (thumbnails can only be made after the original exists, hence the separate channel; the route only backfills existing records — it can't create files from nothing).

**Upstream timeouts (admin-configurable, 2026-07-26):** two tiers, both stored in config (`config.timeouts.{apiTimeoutMs,generationTimeoutMs}`) and edited in admin → 接口配置 → 系统设置 → 请求超时. Read at runtime via `apiTimeoutMs()` / `generationTimeoutMs()`, which `clampTimeoutMs()` into `API_TIMEOUT_RANGE_MS` (10–600s) / `GENERATION_TIMEOUT_RANGE_MS` (30–3600s) and fall back to `DEFAULT_API_TIMEOUT_MS` (300s) / `DEFAULT_GENERATION_TIMEOUT_MS` (1200s). Both accessors read `configStoreCache` on every call, so a change applies to the next request with no restart — `fetchWithTimeout(url, init, timeoutMs = 0)` resolves `0` to `apiTimeoutMs()` at call time, which is why the default parameter must stay `0` and not a constant. The generation tier is passed explicitly at the six `generate*` call sites only; the short tier deliberately covers model list, OAuth and prompt/agent analysis — a hung OAuth redirect must not be able to hang for 20 minutes, which is also why `PUT /api/admin/config/timeouts` rejects `generation < api` with a 400. `generationQueueTtlMs()` is **derived** (`max(30min, generation + 10min)`) rather than a separate knob: if the TTL could fall below the generation timeout, tasks waiting behind full concurrency slots would be judged dead while the system is working normally.

**An AbortController alone is not enough** — Node's built-in fetch (undici) caps `headersTimeout`/`bodyTimeout` at `UNDICI_DEFAULT_TIMEOUT_MS` (300s) and kills the socket first with an opaque `UND_ERR_HEADERS_TIMEOUT`. `longTimeoutDispatcher()` therefore reflects the Agent constructor off `globalThis[Symbol.for("undici.globalDispatcher.1")]` and passes a relaxed-timeout `dispatcher` in the RequestInit (undici is not a declared dependency; PRD §14.1 forbids adding one). Its threshold is `UNDICI_DEFAULT_TIMEOUT_MS`, not the configured API timeout — an admin raising the short tier above 300s needs the relaxed dispatcher too. If reflection ever breaks it silently returns `undefined` and behavior reverts to the 300s cap, with the undici error code translated to Chinese.

**Config center (admin-managed whitelists + presets):** Since 2026-07 the site/model whitelists and the built-in presets are **runtime-configurable via the admin dashboard**, no longer hardcoded. Backend store: `.data/config-store.json` (`ConfigStore` type, `ensureConfigStore`/`readConfigStore`/`writeConfigStore` + in-memory `configStoreCache`), seeded from the former constants on first run. Public snapshot at `GET /api/config` (enabled items only — it is an explicit allowlist, so new private fields like `timeouts` stay server-side by default); admin CRUD under `/api/admin/config`, `/api/admin/config/{upstreams,models,presets,system-prompts,quotas,token-guide,timeouts}` (PUT) and `/api/admin/config/reset` (POST, `{section}`). Every write bumps `version`, updates `updatedAt`, and appends an audit log.
- Upstream sites: managed in admin (name + baseUrl + enabled), served to the frontend. Server-side validation in `validateUpstreamBaseUrl` allows http OR https and IP addresses (so users can point at a bare-IP relay), but still blocks internal/loopback/link-local hosts via `INTERNAL_HOST_PATTERN` (127.x, 10.x, 192.168.x, 172.16–31.x, 169.254.x cloud-metadata, localhost, `*.local`) as SSRF protection. `normalizeAllowedApiBaseUrl` reads enabled upstreams (plus `ALLOWED_API_BASE_URLS` as a permanent fallback that also carries the OAuth provider). At least one enabled site required.
- Models: **exact-match allowlist** managed in admin (id + displayName + `sizing: "explicit-2k4k" | "official-1k"` + enabled). The generate route rejects models not in `enabledModelIds()`. The old fuzzy `includes("image-2")` match is gone from the whitelist path (family helpers like `isGptImage2Model` are still used for sizing behavior).
- Presets (prompt starters, style presets, industry agents, negative prompt): defaults live in the frontend (`PROMPT_STARTERS`, `STYLE_ENHANCEMENT_PRESETS`, `INDUSTRY_AGENTS`, `COMMON_AGENT_NEGATIVE_PROMPT`); config stores overrides. Frontend consumes via module-level `runtime*` vars set by `applyAppConfig`, with the constants as fallback. Admin editor seeds its forms from `override ?? default`.
- System prompts (agent/prompt analyze) and square quotas are also editable and read from config at runtime.
- `tokenGuide` (in-flight on `feat/async-generation`, uncommitted as of 2026-07-26): admin-editable onboarding block telling new users where to get an API key (siteName + tokenUrl + groupName + note). Served in the public `/api/config` snapshot when enabled; written via `PUT /api/admin/config/token-guide`, which rejects non-http(s) `tokenUrl` values.
- `timeouts`: upstream request timeouts, server-side only. The admin form is in **seconds** (filling 1200 beats filling 1200000) and converts to ms on save. See the "Upstream timeouts" section above for the runtime accessors and the clamp ranges.

**Recipes & reference library (client-side assets, 2026-07-27):** two browser-only asset stores added in DB v4, both capped at 50 entries (`RECIPES_LIMIT` / `REFERENCE_LIBRARY_LIMIT` in `shared/db.ts`) and both **never synced to the server** — they are IndexedDB-only, like history. A `Recipe` is a prompt+model+params snapshot, saved and applied from the Studio settings panel (`applyRecipe`, JSON export) *and* from Canvas (node context menu「存为配方」 → `saveNodeAsRecipe`, panel dropdown → `applyRecipeToCanvas`); a `ReferenceLibraryItem` is a stored reference image reused from the Studio upload area and canvas optimize mode. Both live in `shared/db.ts`, so a change to either shape has two consumers (App.tsx and CanvasPage.tsx), not one.

**Frontend API-key lifecycle:** the key lives in React state and is mirrored to `sessionStorage` on **every** `apiConfig` change, *additionally* to `localStorage` only while 记住 API Key is checked (unchecking removes the localStorage copy but the session copy stays — that's why the UI note says "仅保留在本次会话"). Three rules hold: `clearApiKey()` (shared by the 清除 Key button and `oauthLogout()`) must wipe state and *both* stores, since a key may have moved between them; OAuth login writes the provider-issued key but must **not** force `rememberKey: true` — silently upgrading a session-only key to long-term storage overrides an explicit user choice; and the effect watching `apiConfig.apiKey` already resets `models`/`modelState`/`verifiedModelKey` once the key falls below `API_KEY_MIN_LENGTH`, so `clearApiKey()` deliberately doesn't duplicate that.

**Frontend config consumption:** `fetchAppConfig()` runs once per page load (`activePage`-agnostic, in the App mount effect) — decision is "仅进页拉取" (fetch on entry, no polling). Module-level `runtimeEndpoints`/`runtimeModelConfig`/`runtimePromptStarters`/`runtimeStylePresets`/`runtimeIndustryAgents`/`runtimeCommonNegativePrompt` back both JSX and module-level helpers; a `configVersion` state bump forces re-render after the fetch resolves. Saving in the admin also calls `fetchAppConfig(true)` to refresh the same session.

**Admin dashboard tabs:** `AdminApp` is tab-based, five tabs, each hash-deep-linkable (`#admin`, `#admin/logs`, …) — 概览 (stats + model dist + errors + square governance), 请求日志 (paginated request log with saved-image thumbnails), 用户反馈 (`AdminFeedbackPanel`), 接口配置 (`AdminConfigCenter`, sub-tabs 站点与模型 / 提示词与场景 / 系统设置), 安全加固 (`AdminSecurityPanel`). The data-loading effect depends on `adminTab`, so a new tab that needs server data must be added to that dependency list.

If a task seems to require loosening the internal-host constraint in `validateUpstreamBaseUrl` (allowing loopback/private/metadata IPs), confirm with the user — that block is the remaining deliberate SSRF constraint. (The https-only rule was intentionally relaxed to http+IP on 2026-07-20 per the owner.)

**Admin auth:** scrypt-hashed password persisted in `.data/admin-store.json`; in-memory session map with ~8h TTL; cookie-based. The first login forces a password reset.

**Design system (in-flight, 2026-07):** `src/styles.css` is being converged onto a token set defined in `:root` at the top of the file; `docs/design-refresh-prd.md` is the canonical spec. **Write new CSS with these tokens, not literal values** — hardcoding a hex color, a `border-radius: 14px`, or a card shadow silently regresses the refresh. The token groups and the rules they encode:
- Surfaces layer by **transparency overlay, not solid greys and not shadows**: `--bg`/`--surface`/`--surface-soft`/`--overlay-1`/`--overlay-2`, hairline `--border`/`--border-strong`.
- Radius encodes component role, five tiers only: `--r-pill` (buttons/chips) > `--r-panel` 16 (containers) > `--r-card` 12 > `--r-input` 10 > `--r-thumb` 8.
- Motion has two tiers plus a shared curve: `--dur-fast`/`--dur-base`/`--dur-layout` + `--ease`. Animate only `transform`/`opacity`. **`transition: all` is banned** (currently 0 occurrences — keep it that way).
- Shadows are for floating layers only (`--shadow-popover`); cards get hairline + overlay instead.
- Color follows 60/30/10 — brand green ≤10% of screen, reserved for brand moments; semantic `--blue`/`--amber`/`--red` carry state.
- Typography: ≤3 font weights, hierarchy from size/whitespace rather than bold. Global baselines already set at the top of styles.css: `:focus-visible` ring on all interactive elements, `font-variant-numeric: tabular-nums` on body, and a `prefers-reduced-motion` block.

## Privacy model — do not break

The privacy model is load-bearing for this product (README §数据与隐私策略). Since 2026-07 the owner explicitly relaxed the original "no image bytes on the server" rule: generated images ARE persisted to `.data/images/` and referenced from request logs. What still holds:
- Never log API keys. What's allowed is `apiKeyPresent`, `apiKeyLength`, and a **4-char prefix only when the key is ≥ `API_KEY_MASK_MIN_LENGTH` (20)** — `apiKeyLogMeta` is the single producer. There is deliberately **no suffix**: prefix + suffix + exact length together shrink the guessing space, and support only needs to tell two keys apart. A startup scrub in the DB-open path removes `apiKeySuffix` (and over-long prefixes) from legacy `request_logs` rows.
- **Redact credentials by value, not just by key name.** Upstream relays echo keys inside *error strings*, where no key-name match can catch them. `redactCredentialText` (patterns for `sk-`/`AIza…`/`Bearer …`/JWTs/`apikey=…`) runs on every free-text field that reaches storage or the admin UI: `redactImageText`, `safeErrorSummary.message`, both `summaryMessage` sites, `errorKey`, and `requestLogSearchText`. `sanitizeForLog` additionally normalizes key names (`isCredentialKeyName` strips `-`/`_`/spaces, so `x-goog-api-key` and `X_Goog_ApiKey` both match) and handles `[name, value]` header pair-arrays, where the credential name sits in the *value* position.
- **Strip credential headers on cross-origin redirects.** Node's fetch only auto-strips `Authorization`/`Cookie`/`Proxy-Authorization` — **not** custom headers, and this repo sends `x-goog-api-key`. Since upstreams may be plain-http bare IPs, an injected 302 would otherwise hand the user's key to any host. `fetchWithTimeout` therefore uses `redirect: "manual"` and follows hops itself, calling `stripCredentialHeaders` whenever the origin changes (`MAX_REDIRECTS = 5`, non-http(s) targets rejected, 303/301/302-on-POST downgraded to GET). Any new outbound fetch should go through it rather than calling `fetch` directly.
- **Image directory names must stay opaque.** `.data/images/<dir>/…` appears in a public, unauthenticated, `immutable`-cached URL, while `clientId` is the *sole* credential for `/api/tasks` and `/api/images/thumb` — so a directory named after the clientId turns any shared image URL into a credential leak. `imageDirToken()` derives the name as `HMAC(instanceSecret, "image-dir:<kind>:<identity>")` truncated to 24 hex chars. The secret lives in `.data/instance-secret` (mode 600, auto-generated). Losing it only re-buckets *future* images — existing records store relative paths, so nothing breaks. The generate route's disk-quota walk deliberately sums the new token dir **and** the legacy plaintext dir.
- **Anything taking a URL from an upstream response is SSRF-exposed.** `urlToDataUrl` (used when a relay returns `url` instead of `b64_json`) validates every hop with `assertPublicHttpUrl` — which extends `INTERNAL_HOST_PATTERN` with IPv6 loopback/ULA/link-local and bare-integer hosts like `http://2130706433/` — follows redirects manually, enforces a timeout and a 32 MB cap, and identifies the format by **magic bytes** (`sniffImageMime`), since the upstream's `Content-Type` is attacker-controlled.
- Never persist reference-image content to disk or to admin logs (reference images live in an in-memory Map with a ~10-minute TTL only).
- Base64 image payloads never go into `.data/admin-store.json` — logs carry `savedImages` file references (id/mime/bytes), and `sanitizeForLog` still strips any inline image data.
- The browser keeps its full IndexedDB copy; the client must keep working even if a server-side image file has been cleaned up (hence the `dataUrl` fallback in `generatedImageToBlob`).
- The square feed intentionally **does not** return `imageId` — it is a `<dir>/<file>` path and legacy rows still carry plaintext directories. The client only ever renders `thumbnailUrl`.

### Abuse controls that are structural, not cosmetic

- **`createRequestLog` must run only after every validation passes.** Each insert triggers `REQUEST_LOG_LIMIT` trimming, and trimming `unlink`s the evicted rows' image files — so logging rejected requests lets an anonymous caller evict and delete other users' images with junk traffic. The generate route validates first and uses `rejectBeforeLog()` for all failures.
- **Trim order is `(image_count > 0) ASC, created_at ASC`, not pure recency** — image-less rows (analyses, failed generations) are evicted first, so cheap requests can never push image-bearing records out. Verified experimentally: pure-recency order let 50 junk rows delete 10/10 stored images; the current order preserved 10/10.
- Anonymous endpoints share a per-IP token bucket (`anonRateLimit`): generate/analyze/feedback/feature. The per-minute ceilings are **no longer hardcoded** — they read `config.security.{anonGeneratePerMin,anonAnalyzePerMin,anonFeedbackPerMin,anonFeaturePerMin}` at call time via `anonRateLimitFor()` (falls back to `ANON_RATE_DEFAULTS` 60/30/120/5 for 0/invalid). Generation additionally has a per-IP daily quota at `GENERATION_IP_QUOTA_FACTOR ×` the per-clientId limit, since `clientId` is self-reported and trivially rotated.
- **Site hardening is admin-managed (2026-07-27), under the `security` section of `config-store.json`.** Admin login lockout thresholds (`adminMaxFails`/`adminLockMinutes`, read via `adminMaxFails()`/`adminLockMs()` — the old `LOGIN_MAX_FAILS`/`LOGIN_LOCK_MS` consts are gone), the anon rate ceilings above, and an **IP ban list** (`bannedIps: {hash, reason, createdAt}[]`) all live there. Bans are keyed by `clientIpKey()`'s 16-hex HMAC-less sha256 slice — the same value stored in `request_logs.client_ip_hash` — so the admin copies a hash from the security-events view rather than ever seeing a raw IP. `guardBanned(req,res)` (Set cache keyed on `config.version`) sits at the very top of every anon entry point (generate/analyze/agent/feature/feedback) **and** the admin `/login` POST (but NOT authenticated admin actions, so an admin can't lock themselves out mid-session), returning 403. Previously-silent events (`login_fail`/`login_lock`/`rate_limit`/`ban_hit`/`ban_add`) go to an in-memory 500-entry `securityEvents` ring + `securityCounters`; rate-limit events record **once on the crossing** (`count === limit+1`) so a sustained flood can't flush the ring. Admin routes: `GET /api/admin/security` (thresholds + bans + live lockouts derived from `loginAttempts` + recent events + counters), `PUT /api/admin/config/security` (clamps thresholds), `POST /api/admin/security/{ban,unban}` (ban validates the 16-hex shape). Frontend: the `#admin/security` "安全加固" tab (`AdminSecurityPanel`). The `security` section is deliberately **absent** from the public `/api/config` allowlist.
- `POST /api/feedback` and `POST /api/images/thumb` both require the caller's `clientId` to match the record's. `requestId` travels in the public square feed, so without this check anyone could rate (or wipe ratings on) other users' generations — attributed to the victim — and skew the public `/api/model-stats`.
- OAuth `state` is bound to the browser with an `HttpOnly` `imagehub_oauth_state` cookie checked alongside the server-side map. Server-side state alone doesn't stop login CSRF: an attacker can obtain a valid state from `/login` themselves and feed the victim a callback carrying the attacker's `code`, logging the victim into the attacker's account — and that session carries a real upstream key.

If a change would require crossing one of the remaining lines, raise it with the user before implementing.
