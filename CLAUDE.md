# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Product

ImageHub / Image Studio (`codex-image-batch-studio` in package.json) — a local-first batch image-generation workbench. The user fills in an upstream API URL + key, picks an `image-2`-class model, and submits batches; the browser keeps a full copy in IndexedDB, and generated images are also persisted server-side under `.data/images/` (served via `/api/images/local/:id`) so the admin dashboard can review them alongside request logs. Four major feature surfaces: **Studio** (batch generation), **Canvas** (infinite canvas generation mode), **Square** (community gallery with recommend/like), and **Agent Mode A** (NLP-driven brochure planning). Admin dashboard tracks request metadata plus saved-image file references — API keys are never persisted server-side. README.md (Chinese) is the canonical product spec; `docs/agent-mode-brochure-prd.md` is the Agent Mode A spec; `docs/canvas-mode-prd.md` is the Canvas Mode spec.

## Commands

```bash
npm install          # one-time (better-sqlite3 is native, compiles here)
npm run dev          # Vite dev server on http://localhost:8877 (port hardcoded)
npm run build        # tsc -b && vite build  — TypeScript check is gated here
npm run build:server # esbuild-bundle the standalone production server → server-dist/index.mjs
npm run start        # run the production server (serves dist/ + all /api/*), PORT env overrides 8877
./deploy.sh          # full server deployment: deps → build → restart (also start|stop|restart|status|systemd)
```

**Production deployment (since 2026-07):** the backend no longer requires the Vite dev server. `registerApiRoutes(app)` (exported from vite.config.ts) is the single source of truth for all API routes; the dev plugin mounts it on Vite's connect middlewares, and [server/index.ts](server/index.ts) mounts the same function on a plain Node http server with connect-compatible prefix stripping, plus dist/ static hosting (SPA fallback, immutable cache for /assets, no-cache for index.html + build-version.json) and `/healthz`. Taiji OAuth is preserved: env vars come from `.env` (template auto-generated by deploy.sh); redirect URI auto-derives from Host/X-Forwarded-Proto when `OAUTH_REDIRECT_URI` is unset, so it works behind nginx.

There is **no test framework, ESLint, Prettier, Biome, or pre-commit hook** in this repo — don't go hunting for them. There is no standalone `typecheck` script either; `tsc -b` runs as part of `npm run build`. Use that to check types.

Admin defaults: `admin` / `admin123456` at `http://localhost:8877/#admin`. Override via env: `ADMIN_USERNAME=... ADMIN_INITIAL_PASSWORD=... npm run dev`.

## Architecture — the non-obvious parts

**The entire backend lives inside `vite.config.ts`** (~4220 lines). It registers a custom Vite plugin whose `configureServer` middleware implements every `/api/*` route. There is no `server/`, `api/`, or `backend/` directory. When the task involves request logging, admin auth, the upstream proxy, or reference-image temp URLs, edit `vite.config.ts`, not files under `src/`.

Server-side route groups:
- `/api/models`, `/api/images/generate`, `/api/temp-reference/:id` — core generation proxy.
- `/api/admin/*` (login, logout, change-password, stats, requests, me) — admin dashboard.
- `/api/square/*` (feed, quota, recommend, like, image/:id, admin/overview, admin/export) — community gallery. Data persisted to `.data/square-store.json`. Feed/quota GET endpoints authenticate via `x-imagehub-api-key` header (not query params). Thumbnails are served as binary from `/api/square/image/:id` with long cache headers — the feed response returns `thumbnailUrl` (not inline base64).
- `/api/agent/analyze` — Agent Mode A intent classification (single_image, multi_image_batch, brochure_project, page_refine).

**The entire frontend lives inside `src/App.tsx`** (~11200 lines). One monolithic component handles home, studio, canvas, square, and admin views via an `activePage` state switch (`"home" | "studio" | "square" | "admin" | "canvas"`) — there is no router, no Redux/Zustand, no React Context for app state. State is `useState` + `useRef` (the generation queue uses `pendingQueueRef` deliberately to avoid re-renders mid-pump). Styles are in `src/styles.css` (~7900 lines) as plain CSS with custom properties.

**Canvas Mode (infinite canvas):** `CanvasPage` component — a 2D pan/zoom canvas where users generate images as nodes and build visual iteration trees. URL hash `#canvas`. Layout: left = infinite canvas (DOM + CSS `transform` approach), right = 360px collapsible panel. Nodes stored as `CanvasNode[]` with position/status/image data. Edges (`CanvasEdge[]`) visualize parent→child optimization lineage via SVG bezier curves. Canvas state persisted to IndexedDB stores `canvas-state` (single "current" key) and `canvas-images` (keyed by nodeId). Key state: `canvasNodes`, `canvasEdges`, `viewport` ({x,y,zoom}), `selectedNodeId`, `panelMode` ("generate" | "optimize"). Generation reuses existing `/api/images/generate` — no new backend endpoints. Reference image compression for optimization uses `createSquareThumbnail()` (max edge 1024px, WebP 0.82).

**Model variants:** `gpt-image-2` and `gpt-image-2-pro` use explicit 2K/4K size options (`GPT_IMAGE_2_SIZE_OPTIONS`) instead of pure aspect-ratio scaling, including duplicate-ratio 2K choices such as `2560x1440` and `2048x1152`. Other image-2 family models still fall back to fixed official 1K sizing via `usesOfficialGptImageSizing()`. Keep the frontend and backend size tables in sync.

**Square (community gallery):** users can recommend generated images to a shared feed. Browse by latest/hot/top; daily quotas (10 recommends, 10 likes). Admin has overview + CSV/JSON export. Square state is server-persisted in `.data/square-store.json`, not IndexedDB.

**Agent Mode A (brochure workflow):** toggleable mode that NLP-parses the prompt into an intent (single image → direct generation, multi-image batch → parallel generation, brochure project → multi-page planning with style-board selection). Brochure flow: analyze → plan → generate 4 style boards → user picks one → refine individual pages. Key state: `isAgentModeEnabled`, `agentModeState`, `agentModePendingPlan`, `agentModeBrochureDraft`.

**Data storage (SQLite + JSON + files):** As of 2026-07 request/generation records live in **SQLite** (`.data/imagehub.db`, via `better-sqlite3`), not JSON. The `request_logs` table has indexed columns (status, model, error_key, created_at, ref/upstream/image flags) plus a `data` TEXT column holding the full `RequestLog` JSON. `createRequestLog`/`updateRequestLog` are the only writers (`requestLogRow` upserts); reads are in `/api/admin/{stats,requests,requests/:id,logs/export}`. On first DB open, legacy `admin-store.json` `requestLogs` are migrated in once and cleared. Kept at 5000 rows (oldest trimmed, their image files deleted). **Still JSON:** admin users + audit logs (`admin-store.json`), config (`config-store.json`), square data (`square-store.json`) — these are config-like, not append-heavy records. `better-sqlite3` is a native dep (`npm install` compiles it); `@types/better-sqlite3` is a devDep.

**Image storage (per-user folders):** Generated images are saved to `.data/images/<userDir>/<requestId>[-<index>].<ext>` — `userDir` is the OAuth username or (sanitized) clientId, filename is the generation's `requestId`. Served via `/api/images/local/<userDir>/<file>` with `LOCAL_IMAGE_PATH_PATTERN` + `..` guard + `startsWith(LOCAL_IMAGE_DIR)` check against traversal. `savedImages[].id` stores the relative `<userDir>/<file>` path. Each generate call already has a unique `requestId` (randomUUID) = the per-submission ID.

**Analytics & feedback (2026-07):** Two more SQLite tables beyond `request_logs`: `daily_stats` (date+model PK, incremented once when a generation reaches terminal state via the `updateRequestLog` running→terminal transition guard; backfilled from existing logs when empty — daily trends survive the 5000-row trim) and `image_feedback` (one 👍/👎 per requestId, upserted via public `POST /api/feedback`). `GET /api/model-stats` (public) returns 7-day per-model successRate/P50/samples/ratings; the studio model picker renders this under each model (needs ≥3 samples). **Metric scoping:** `/api/admin/stats` headline numbers, modelCounts and errorCounts count image_generation requests ONLY (`analysisCount` reported separately); latency is P50/P95 over successful generations, not mean. Generation quotas live in config `quotas`: `generationDailyLimit` (per clientId per Shanghai calendar day) and `userDiskLimitMB` (per user image dir, walked with statSync) — 0 = unlimited, enforced in the generate route with HTTP 429.

**Full error capture:** On generation failure the log stores `errorFull` — the complete upstream/relay error body (image data redacted, capped at 60k chars, not the 800/2500 truncation used for the summary fields). Rendered in the admin request detail as a red "完整错误内容" panel. This exists specifically to debug relays that return a 200/OK-looking response but actually failed generation.

**Generation pipeline:**
1. Client builds `Job` objects, pushes them onto `pendingQueueRef.current`, and `pumpQueue()` drains them respecting client-side `concurrency` (1–6).
2. Each job POSTs to `/api/images/generate` with `{ baseUrl, apiKey, request: { protocol, model, prompt, referenceImages, aspectRatio, seed, ... } }`.
3. Reference images are sent as data URLs; the Vite middleware stashes them in an in-memory `temporaryReferences` Map with a ~10-minute TTL, generates `/api/temp-reference/{id}` URLs, and forwards those URLs (not base64) to the upstream `/v1/images/generations` endpoint.
4. On success the server persists each generated image to `.data/images/<userDir>/<requestId>[-<index>].<ext>` (`persistGeneratedImages`) and replaces the base64 `dataUrl` in the response with a local URL (`/api/images/local/<userDir>/<file>`, served with immutable cache headers). The SQLite request record stores `imageSaved` + `savedImages` metadata (id=relative path, mime, bytes) — the admin dashboard renders these as thumbnails in the log detail view. Records are capped at 5000; trimmed ones get their image files deleted too (`deleteSavedImages`).
5. Server logs request metadata — `requestId`, prompt, model, params, status, duration, error class, saved-image file references — to `.data/admin-store.json`. Never the API key.
6. Client fetches the image blob from the local URL (`generatedImageToBlob`, with `dataUrl` fallback) and stores the Blob + history record in IndexedDB as before.

**Config center (admin-managed whitelists + presets):** Since 2026-07 the site/model whitelists and the built-in presets are **runtime-configurable via the admin dashboard**, no longer hardcoded. Backend store: `.data/config-store.json` (`ConfigStore` type, `ensureConfigStore`/`readConfigStore`/`writeConfigStore` + in-memory `configStoreCache`), seeded from the former constants on first run. Public snapshot at `GET /api/config` (enabled items only, excludes systemPrompts/quotas); admin CRUD under `/api/admin/config`, `/api/admin/config/{upstreams,models,presets,system-prompts,quotas}` (PUT) and `/api/admin/config/reset` (POST). Every write bumps `version`, updates `updatedAt`, and appends an audit log.
- Upstream sites: managed in admin (name + baseUrl + enabled), served to the frontend. Server-side validation in `validateUpstreamBaseUrl` allows http OR https and IP addresses (so users can point at a bare-IP relay), but still blocks internal/loopback/link-local hosts via `INTERNAL_HOST_PATTERN` (127.x, 10.x, 192.168.x, 172.16–31.x, 169.254.x cloud-metadata, localhost, `*.local`) as SSRF protection. `normalizeAllowedApiBaseUrl` reads enabled upstreams (plus `ALLOWED_API_BASE_URLS` as a permanent fallback that also carries the OAuth provider). At least one enabled site required.
- Models: **exact-match allowlist** managed in admin (id + displayName + `sizing: "explicit-2k4k" | "official-1k"` + enabled). The generate route rejects models not in `enabledModelIds()`. The old fuzzy `includes("image-2")` match is gone from the whitelist path (family helpers like `isGptImage2Model` are still used for sizing behavior).
- Presets (prompt starters, style presets, industry agents, negative prompt): defaults live in the frontend (`PROMPT_STARTERS`, `STYLE_ENHANCEMENT_PRESETS`, `INDUSTRY_AGENTS`, `COMMON_AGENT_NEGATIVE_PROMPT`); config stores overrides. Frontend consumes via module-level `runtime*` vars set by `applyAppConfig`, with the constants as fallback. Admin editor seeds its forms from `override ?? default`.
- System prompts (agent/prompt analyze) and square quotas are also editable and read from config at runtime.

**Frontend config consumption:** `fetchAppConfig()` runs once per page load (`activePage`-agnostic, in the App mount effect) — decision is "仅进页拉取" (fetch on entry, no polling). Module-level `runtimeEndpoints`/`runtimeModelConfig`/`runtimePromptStarters`/`runtimeStylePresets`/`runtimeIndustryAgents`/`runtimeCommonNegativePrompt` back both JSX and module-level helpers; a `configVersion` state bump forces re-render after the fetch resolves. Saving in the admin also calls `fetchAppConfig(true)` to refresh the same session.

**Admin dashboard tabs:** `AdminApp` is tab-based — 概览 (stats + model dist + errors + square governance), 请求日志 (paginated request log with saved-image thumbnails), 接口配置 (renders `AdminConfigCenter` with sub-tabs 站点与模型 / 提示词与场景 / 系统设置).

If a task seems to require loosening the internal-host constraint in `validateUpstreamBaseUrl` (allowing loopback/private/metadata IPs), confirm with the user — that block is the remaining deliberate SSRF constraint. (The https-only rule was intentionally relaxed to http+IP on 2026-07-20 per the owner.)

**Admin auth:** scrypt-hashed password persisted in `.data/admin-store.json`; in-memory session map with ~8h TTL; cookie-based. The first login forces a password reset.

**Frontend version banner:** `vite.config.ts` computes `FRONTEND_BUILD_VERSION` from the latest mtime across `src/`, `vite.config.ts`, and `package.json`; the client polls `/build-version.json` to detect deploys. Don't strip this if you're refactoring the config.

## Privacy model — do not break

The privacy model is load-bearing for this product (README §数据与隐私策略). Since 2026-07 the owner explicitly relaxed the original "no image bytes on the server" rule: generated images ARE persisted to `.data/images/` and referenced from request logs. What still holds:
- Never log API keys (the existing code logs only `apiKeyPresent`, `apiKeyLength`, and a 4-char prefix).
- Never persist reference-image content to disk or to admin logs (reference images live in an in-memory Map with a ~10-minute TTL only).
- Base64 image payloads never go into `.data/admin-store.json` — logs carry `savedImages` file references (id/mime/bytes), and `sanitizeForLog` still strips any inline image data.
- The browser keeps its full IndexedDB copy; the client must keep working even if a server-side image file has been cleaned up (hence the `dataUrl` fallback in `generatedImageToBlob`).

If a change would require crossing one of the remaining lines, raise it with the user before implementing.
